# Урок 2. GROUP BY и JOIN

## 1. От одной таблицы к нескольким

На прошлом занятии вся база была одной таблицей `students(id, name, grade)`. Это работает, пока у каждого студента ровно одна оценка. Но в жизни студент учится на нескольких курсах, и у каждого курса — своя оценка. Если попытаться впихнуть это в одну таблицу, получится дублирование:

| id | name | course   | grade |
|----|------|----------|-------|
| 1  | Аня  | Python   | 5.0   |
| 2  | Аня  | SQL      | 4.5   |
| 3  | Борис| Python   | 3.5   |

Имя "Аня" повторяется, и если она поменяет имя — придётся исправлять его в нескольких строках. Это та же проблема, что в уроке 1 мы обсуждали для плоских файлов: данные должны жить **в одном месте**, а не копироваться.

Решение — **нормализация**: разбить данные на несколько таблиц так, чтобы каждый факт хранился один раз, и связать их через ссылки на первичный ключ (**внешний ключ**, foreign key):

```sql
CREATE TABLE students (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE courses (
    id    INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    hours REAL
);

CREATE TABLE enrollments (
    id         INTEGER PRIMARY KEY,
    student_id INTEGER NOT NULL REFERENCES students(id),
    course_id  INTEGER NOT NULL REFERENCES courses(id),
    grade      REAL
);
```

`enrollments` — таблица-связка: одна строка = "этот студент записан на этот курс, вот его оценка". Имя студента и название курса теперь существуют ровно в одном месте. Но за это приходится платить: чтобы получить "имя студента + название курса" в одном результате, одной таблицы уже не хватает — нужен **JOIN**.

### Зачем нормализация: три вида аномалий

Если хранить всё как одну широкую таблицу "студент + курс + оценка" (как в примере выше), дублирование конкретно проявляется в трёх видах проблем:

- **Аномалия вставки (insert anomaly)** — нельзя добавить курс, если на него пока никто не записался: столбцы `course`/`hours` существуют только внутри строки с конкретным студентом, а строки без студента просто нет.
- **Аномалия обновления (update anomaly)** — если курс "Python" упомянут в десяти строках и его переименовали в "Python для начинающих", нужно исправить все десять строк. Забыл хотя бы одну — и данные стали противоречивы: одна и та же сущность называется по-разному в разных строках.
- **Аномалия удаления (delete anomaly)** — если удалить последнего студента, записанного на курс "История", вместе с ним исчезнут и сведения о самом курсе (его `hours`), хотя курс как сущность никуда не пропадал — просто на него никто не ходит.

Нормализация устраняет все три: каждый факт (имя студента, название курса, его продолжительность) хранится ровно в одной строке одной таблицы, и операция с одной сущностью (добавить, переименовать, удалить) не задевает другую.

### Уровни нормализации

Нормализация — не одно разовое действие, а последовательность всё более строгих правил, "нормальных форм". Каждая следующая форма предполагает выполнение предыдущей плюс добавляет своё требование. На практике для большинства задач достаточно дойти до третьей:

| Форма | Требование | Нарушение в нашем примере |
|---|---|---|
| **1NF** (первая) | каждый столбец хранит одно атомарное значение, нет повторяющихся групп и списков в ячейке | столбец вида `courses = "Python, SQL"` в одной ячейке у студента — список нужно разбить на отдельные строки |
| **2NF** (вторая) | 1NF + каждый неключевой столбец зависит от **всего** составного ключа, а не только от его части | если первичный ключ `enrollments` — пара `(student_id, course_id)`, а в этой же таблице хранить ещё и `course_title` — он зависит только от `course_id`, то есть от части ключа. Это нарушение: `course_title` должен жить в отдельной таблице `courses`, где `course_id` — целый первичный ключ |
| **3NF** (третья) | 2NF + нет транзитивных зависимостей между неключевыми столбцами (неключевой столбец не должен зависеть от другого неключевого столбца) | если бы в `students` хранились `city` и `city_population`, то `city_population` зависит от `city`, а не напрямую от `id` студента — тоже нужна отдельная таблица `cities` |

Более строгие формы (BCNF, 4NF, 5NF) существуют, но в прикладных задачах к ним обращаются редко. Важнее сам принцип за ними: **каждый неключевой столбец должен зависеть от ключа своей таблицы, и только от него**. Ровно это получилось, когда мы разбили одну таблицу на `students`, `courses` и `enrollments`.

Обратная сторона нормализации — больше таблиц и больше `JOIN`'ов в каждом запросе. Позже в курсе встретится и обратный приём — **денормализация** (сознательное дублирование данных ради скорости чтения), но это осознанный компромисс для конкретной задачи, а не вариант по умолчанию. Начинать стоит с нормализованной схемы.

## 2. JOIN — соединение таблиц

`JOIN` берёт строки из двух таблиц и склеивает те, что соответствуют условию (обычно: внешний ключ в одной таблице равен первичному ключу в другой).

```sql
SELECT students.name, courses.title
FROM enrollments
JOIN students ON students.id = enrollments.student_id
JOIN courses ON courses.id = enrollments.course_id;
```

Что происходит: для каждой строки `enrollments` ищется строка `students` с совпадающим `id` и строка `courses` с совпадающим `id`, и все три строки склеиваются в одну. `JOIN ... ON ...` — это и есть "как связать таблицы".

### INNER JOIN — только совпадения

`JOIN` по умолчанию — это `INNER JOIN`: в результат попадают только те строки, для которых совпадение найдено **в обеих** таблицах. Если у курса "История" никто не записан, он вообще не появится в результате `enrollments JOIN courses` — для него просто нет строки в `enrollments`, с которой можно было бы соединиться.

### LEFT JOIN — все строки слева, даже без пары

Если нужно сохранить все строки из "левой" таблицы, даже если для них нет соответствия справа — используется `LEFT JOIN`. Непарные столбцы справа заполняются `NULL`:

```sql
SELECT students.name, courses.title
FROM students
LEFT JOIN enrollments ON enrollments.student_id = students.id
LEFT JOIN courses ON courses.id = enrollments.course_id;
```

Теперь Егор, который ни на один курс не записан, попадёт в результат — просто с `NULL` вместо названия курса. Это стандартный приём, чтобы найти "у кого чего-то нет": студентов без курсов, заказы без оплаты, курсы без единого студента — всегда `LEFT JOIN` + `WHERE правая_таблица.id IS NULL`:

```sql
-- студенты без единого курса
SELECT students.name
FROM students
LEFT JOIN enrollments ON enrollments.student_id = students.id
WHERE enrollments.id IS NULL;
```

| | Что остаётся в результате |
|---|---|
| `INNER JOIN` | только строки, у которых есть пара в обеих таблицах |
| `LEFT JOIN` | все строки левой таблицы; если пары нет — `NULL` вместо правых столбцов |

## 3. GROUP BY — агрегация по группам

В уроке 1 агрегатные функции (`COUNT`, `AVG`, `MAX`, `MIN`, `SUM`) сворачивали **всю таблицу** в одно число. `GROUP BY` разбивает таблицу на группы по значению столбца и считает агрегат **для каждой группы отдельно**:

```sql
SELECT courses.title, AVG(enrollments.grade)
FROM enrollments
JOIN courses ON courses.id = enrollments.course_id
GROUP BY courses.id;
```

Это читается так: "сгруппируй строки `enrollments` (уже склеенные с `courses`) по курсу, и для каждой группы посчитай средний `grade`". Результат — одна строка на курс, а не одна строка на запись о зачислении.

**Правило**, которое СУБД заставляет соблюдать: в `SELECT` при наличии `GROUP BY` можно упоминать только столбцы, по которым идёт группировка, и агрегатные функции. `SELECT students.name, courses.title` при `GROUP BY courses.id` не имеет смысла — для одной группы (курса) может быть несколько разных имён студентов, и непонятно, какое из них показывать.

### COUNT(*) vs COUNT(столбец)

Это различие уже встречалось в уроке 1 и здесь особенно важно при `LEFT JOIN`:

```sql
SELECT students.name, COUNT(enrollments.id)
FROM students
LEFT JOIN enrollments ON enrollments.student_id = students.id
GROUP BY students.id;
```

Для Егора (без курсов) `LEFT JOIN` создаёт одну строку с `enrollments.id = NULL`. `COUNT(*)` посчитал бы эту строку и выдал 1 — неверно. `COUNT(enrollments.id)` игнорирует `NULL` и правильно выдаёт 0.

## 4. HAVING — фильтр по группам

`WHERE` фильтрует строки **до** группировки. Что если нужно отфильтровать уже посчитанные группы — например, оставить только курсы со средним баллом не ниже 4? На момент выполнения `WHERE` агрегат `AVG(grade)` ещё не существует, поэтому `WHERE AVG(grade) >= 4` — ошибка. Для фильтрации по результату агрегатной функции есть отдельное ключевое слово — `HAVING`, оно выполняется **после** `GROUP BY`:

```sql
SELECT courses.title, AVG(enrollments.grade)
FROM enrollments
JOIN courses ON courses.id = enrollments.course_id
GROUP BY courses.id
HAVING AVG(enrollments.grade) >= 4;
```

| | Когда срабатывает | Что фильтрует |
|---|---|---|
| `WHERE` | до `GROUP BY` | отдельные строки |
| `HAVING` | после `GROUP BY` | готовые группы (можно использовать агрегаты) |

`WHERE` и `HAVING` можно использовать в одном запросе одновременно — они отвечают за разные этапы.

## 5. Порядок выполнения запроса

SQL-запрос пишется в одном порядке (`SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT ...`), но выполняется в другом — это и объясняет, почему `WHERE` не видит агрегаты, а `HAVING` видит:

```
FROM / JOIN  →  WHERE  →  GROUP BY  →  HAVING  →  SELECT  →  ORDER BY  →  LIMIT
```

Сначала собираются и соединяются таблицы, затем отфильтровываются строки, затем группировка, затем фильтр по группам, и только потом вычисляется список столбцов для вывода.

## 6. Мостик к Python

```python
import sqlite3

conn = sqlite3.connect("school.db")
cursor = conn.cursor()
cursor.execute("""
    SELECT courses.title, AVG(enrollments.grade)
    FROM enrollments
    JOIN courses ON courses.id = enrollments.course_id
    GROUP BY courses.id
    HAVING AVG(enrollments.grade) >= 4;
""")
for title, avg_grade in cursor.fetchall():
    print(title, avg_grade)
conn.close()
```

То же самое в Python без SQL потребовало бы собрать словарь курс → список оценок, пройтись по нему и посчитать средние вручную — `GROUP BY` делает это в одной строке декларативно.
